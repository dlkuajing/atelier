# 真机 CODE V 视场缩减 A/B（2026-07-28）

**一句话**：**PR #101 自己标注的最大限制被真机推翻了。**
CODE V **也**在砍视场后恢复失败 seed（8 颗严格失败里 **4 颗完全恢复、1 颗部分**），
而 CODE V **是会迭代求主光线的**——所以视场效应**不是 Optiland 缺 ray aiming 造成的假象**。
同时异质性在生产引擎里复现：**3/8 砍到 1/4 视场仍不恢复**。

## 这个实验是为了拆掉哪个混淆

PR #101 的离线消融显示失败 seed 在砍视场后恢复，但当时写明了一条限制：

> Optiland 没有 ray aiming。光阑在镜组内部时，边缘视场光线朝**近轴入瞳**发射；
> 缩小视场会减小光瞳像差，**对任何镜头**都让光线更易通过。
> 所以视场臂**本身不能证明声明视场是错的**。

这个混淆**离线拆不掉**。CODE V 会迭代求主光线（其主导报错正是
`Unable to find chief ray`，说明它在迭代），所以同一操作在 CODE V 上重做即可判别。

## 设置

- **对象**：`data/zmx` 中**严格失败 ∧ 保真度干净**的专利 seed，共 8 颗
- **自变量只有一个**：把 ZMX 的 `YFLN` 记录整体乘以系数，**离线改**、写工作副本，
  **`data/zmx` 全程零写入**
- **导入走生产路径**：`zmx_import_prep.stage_zmx_for_codev`，读回 `NUM W = 3`
- **判据**：与逐视场普查同一把尺子——每个视场 `SPOTDATA` 成功且点列径 `> 0`。
  探针把失败编码为 `-1`；`0.0` 同样不算通过（它是「完美点像」形态的退化值）
- **红线①**：每次运行前后均实测 `codev`/`codevm` **会话数 = 0**（判据为
  「父进程非 codev/codevm 的实例数」），全程无泄漏

**阳性对照（这条不做，阴性结果就没有意义）**：健康 seed `US-10120164-B2-e2`
在 1.0× 下 **2/2 出数**，证明探针能产出正数。它在 0.7× 下边缘视场
RMS 从 942.12 → 698.35 µm，物理方向合理，证明视场缩减确实生效。

## 结论

1. **视场效应在生产引擎里是真的**，不是 Optiland 光瞳处理的产物。
   PR #101 那条「有判别力的是恢复形状，但不能证明声明视场有错」的限制，
   **在「是不是引擎假象」这一维上已被拆除**。
2. **异质性复现**：3/8 砍到 1/4 视场仍不出数——这些不是「视场要太多」，是别的东西坏了。
   与 #101 的逐颗分类（硬核 5 / 35）方向一致。
3. ⚠️ **仍然不能推出「声明视场是错的」**。砍视场对**任何**镜头都更容易通过，
   CODE V 也不例外。本实验证明的是**失败对视场量级敏感、且这种敏感是真实光学的**，
   **不是**「专利写的视场值错了」。要证后者，仍需拿专利原文的 FOV 定义逐颗核对。

## 探针的一个未解怪癖（已隔离影响面，结论不受污染）

**17 颗真实设计（文件名含点，如 `5P_F2.0_FOV78.7_...`）在本探针下被 CODE V 读成
`num_fields=1 / NUM W=1`**，而同一文件改成无点名后读成 `12 / 5`（与逐视场普查一致）。
四格隔离实测确认是**文件名**而非目录，且**与路径长度无关**
（60 字符点名失败、160 字符无点名成功）。

**但这不是生产缺陷——已实测排除**：生产入口 `run_codev_readout` 用**同一个点名文件**
读出 `num_fields=12 / num_wavelengths=5`，正确。
字节链也已核对：源 → 缩放副本 → 生产 staging **三者完全一致**，`IN` 行与生产**逐字相同**。
差异只剩「本探针在导入后定义了一个 `FCT`」，但该形态在无点长名下又正常，**故仍未解释**。

**处理**：所有真实设计**已从本实验剔除**，表中只有专利 seed（文件名无点）。
一度写下的「生产路径也中招、影响 17 颗真实设计」**是错的，已收回**。

## 本轮踩的两个坑

1. **首次运行绕过了生产的多波长预处理**——探针直接导入缩放副本，
   读回 `NUM W = 1`，等于复现 PR #93 修复前的单波长塌缩态。
   **是探针自己的输出（`num_wavelengths: 1`）暴露的**。已改为先缩放、再过
   `stage_zmx_for_codev`，顺序不可颠倒。
2. **双 BOM**：把 UTF-16 的 BOM 当文本读进来，写回时又加一次
   （26634 → 26636 字节，开头 `fffe fffe`），破坏首条记录。
   已在 `read_zmx_text` 里 `lstrip` 掉；修后 `scale=1.0` 对 UTF-16 文件**字节完全一致**。
