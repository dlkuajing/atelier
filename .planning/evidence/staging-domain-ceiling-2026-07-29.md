# 扩底库「先量再采」第一步：staging 池域内上界 = 40 颗（2026-07-29）

**一句话**：主公裁定投入扩底库后，先量了 staging 池 613 颗在**三把尺子**下能补多少。
答案是**最多 40 颗（上界）**——而且衰减最狠的一级是**第三把尺子**（205 → 40，只剩 19.5%）。

**这直接改变扩底库该怎么做：与其「采更多」，不如「按域采」。**

## 三级衰减

| staging 池 613 颗 | 数 | 说明 |
|---|---|---|
| ① 严格可追迹 | 238 | 全视场出数 |
| ② ∧ 保真度干净 | 205 | 非球面系数未被剥 |
| ③ ∧ 四轴过手机 `SCENARIO_BOUNDS` | **40** | ← **上界** |

**合计上界：55（`data/zmx` 现有域内）+ 40 = 95 颗。**

## 为什么是上界，不是实数（两个来源，都只会让真数更小）

1. **未含 IMH 判据**。staging 的 conversion receipt 里没有 `image_height_mm`，
   四轴只用了 EFL / F# / FOV / 片数。而 IMH 在 `data/zmx` 上是**第 3 大越界项**
   （44 次），加上它只会更少
2. **118 颗对不上 receipt** 已被排除。这是 key 构造（`{patent_id}-e{N}`）覆盖不全，
   **不是它们没有 receipt**；它们里也会有一部分不合格

## 口径不完全一致（必须知情）

- staging 用的是**专利声明值**（`focal_length_mm` / `f_number` / `hfov_deg`，
  取自 `data/patent-conversion-attempts/local-replay/*/attempt-*/request.json`）
- `data/zmx` 那 55 颗用的是 case index 的**实算值**

两者不是同一把尺子的同一刻度。**跨池相加（95）只能当量级参考，不能当精确数。**

## 对扩底库策略的直接后果

**把整个 staging 池提升为可路由，域内底库最多从 55 到 95——不到翻倍。**
而现在 55 颗只撑得起 **30 条 trial / 5–8 颗独立 seed**；翻倍**大概率仍不够**
支撑有统计意义的打平率。

**真正的瓶颈不是 staging 没提升，是转出来的东西大量落在产品域外**——
第三把尺子砍掉 205 → 40。

→ **建议：在采集/转换阶段就按产品域筛**（USPTO 检索时按 EFL / F# / FOV / 片数 过滤），
否则转出来八成还是域外的，重复现在这条衰减曲线。

## 未做

- **IMH 判据未接**（需要为 staging 补实算像高）
- **118 颗未匹配的 receipt 未追**（key 构造问题，不是数据缺失）
- 转换尝试制品 752 与 USPTO 续采**未按三把尺子评估**
- 40 这个数**未经真机复核**，纯离线声明值推算
