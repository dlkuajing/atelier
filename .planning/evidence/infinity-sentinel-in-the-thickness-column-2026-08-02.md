# 八颗镜头的像面被放到 1e18 mm 外（2026-08-02）

> ⚠️ **标题与根因已在合并前修正。** 初版叫「专利表里的 `1E+18` 落在厚度列」并把根因
> 写成「厚度列没有护栏」——**那是误诊**，见下面「根因更正」一节。真根因在标签分词。

## 症状

语料里有 8 颗的读数不是「大」，是**物理上不存在**：

| | |
|---|---|
| `index.json` 的 `image_height_mm` | **5.8e17 ~ 8.3e17 mm** |
| CODE V 全场点列直径 | **2.3e20 ~ 1.2e21 µm**（其中 5 颗有全场读数） |
| 畸变 | **恰好 0.0**（8 颗里 7 颗 0.0、1 颗 1.14e-14） |
| EFL | **正常**，与专利声明值一致 |

名单：`US-11719917-B2-e2/e3/e4/e5/e6`、`US-12032139-B2-e2/e4/e6`。

## 病灶：一行

**末面（像面）的 `DISZ 1e+18`** —— 像面被放到 1e18 mm 外。

**集合相等，不是相关**：全库 1055 颗 ZMX 里
「末面 `DISZ` ≥ 1e12」与「任一视场点列 ≥ 1e6 mm」是**同一个 8 元素集合**，零假阳零假阴。

三个独立读数在量上都对得上：

- 存库像高 = `1e18 × tan(主光线出射角)` → 反解出 **30.3°–39.6°**，全是手机镜头合理的 CRA
- 点列直径 / 1e18 ≈ **1/F#**（比值 0.71–0.83，就是 F# 光锥在 1e18 mm 上的张开）
- **畸变塌成恰好 0**：`L→∞` 时实高与参考高都趋于 `L·tanθ` 而相消
  ——「退化值恰等于理想读数」在本项目的第 12 例
- **EFL 不受影响**，因为它是近轴量、与像面位置无关 —— **这正是它骗过所有入库闸的原因**

## ⚠️ 根因更正：不是「厚度列没护栏」，是**标签少吃了一个 token**

**本节是合并前对抗审查推翻本 PR 初版诊断后重写的。初版说错了。**

初版写的是「专利表用 `1E+18` 印无穷，半径列两层护栏、厚度列零层」。
真相由**仓库自己的金标 fixture** 给出（`tests/test_patent_to_zmx.py` 的 Ability Opto 表）：

```
10 Image plane 1E+18 0
```

`_consume_surface_label` 把 `IMAGE` 放在一个**只吃一个 token** 的集合里
（`scripts/patent_to_zmx.py:76361`），于是：

| | 应该解析成 | 实际解析成 |
|---|---|---|
| 标签 | `Image plane` | `Image` |
| 半径 | `1E+18`（→ plano） | `plane`（→ plano，碰巧也对） |
| 厚度 | `0` | **`1E+18`** ← 病 |
| 残留 | — | `0` 被当尾随残留丢掉 |

⇒ **那个值从来不属于厚度列。**`_request_radius_mm` 本来就会在它自己的列里接住它，
只是它根本没走到那儿。产物逐位吻合：`US-11719917-B2-e2.zmx` 末面 `CURV 0 / DISZ 1e+18`，
真正的后焦 `0.999` 在倒数第二面上。

**为什么不在本 PR 里一行修掉**：同一个函数的 `APERTURE` 分支注释自己写着
Ability 的表也写 `Aperture plane -0.412`，那一行里 `plane` **确实是半径列**。
两者靠 token 数分辨不可靠，需要单独一铲，不能在合并 session 里顺手拍。

**那本 PR 改的是什么**：**围堵，不是修复**。它把静默的 `DISZ 1e+18` 变成
「要么采用语料约定、要么大声失败」，并让审计能看见这一类。
⚠️ **末面映射成 0 在这 8 颗上恰好等于真值，是侥幸不是保证** ——
`position == len-1` 证明不了某一行是像面行：语料里 **42 颗**的末面 `DISZ` 是**真实后焦**
（最大 72 mm，如 `US-12345855-B2-e4.zmx`）。

正向对照仍然成立：`US-10514523-B2` 的 **38 行半径**就是 `1e+18` 却安然无恙 ——
半径列的编码确实生效，问题出在值根本没进那一列。


## 修了什么

1. **`_is_infinity_sentinel`**：`math.inf` 与数值型 `1e18` 走**同一个判定**。
   `_request_radius_mm` 改用它（行为不变，只是把隐式的运气变成显式的规则）。
2. **`_request_thickness_mm`**（新，与半径侧对称）：
   - **末面** → `0`。语料自己的写法就是 `0`（442 颗里 **392** 颗），属**采用既有约定**不是编数。
     ⚠️ 但 `position == len-1` **证明不了**某行是像面行——42 颗的末面是**真实后焦**；
     这 8 颗上答案对，是因为它们真厚度确实是 0。
     ⚠️ 副作用：`INFINITY` 拼写的末面厚度从 DTO 硬拒（`allow_inf_nan=False`）变成静默 `0.0`。
   - **任何中间面** → **fail closed 抛错**。中间的无穷空气隙是列错位，不是气隙；
     读不出来的设计比读成别的东西的设计好。
3. **`corpus_fidelity_audit` 加 `separation_beyond_physical_scale`**：它此前
   **从不读 `DISZ`**，所以 8 颗一颗没拦。加上后隔离名单 `data/zmx` 55 → **63**，
   staging 不变（80）。**已出厂的 8 颗因此立刻退出可用池，不需要重生成语料。**

### 截断值不是调出来的

两池 17452 条 `DISZ` 记录里，**最大的真实间隔是 1200 mm，下一个值就是 1e+18**
——中间空着 15 个数量级。`1e6` 只是落在这道空档里的一点。
测试 `test_the_magnitude_cut_sits_in_a_void` 每次重测这道空档；
一旦真实数据靠近它，切点就必须重推而不是沿用。

`DISZ INFINITY` / `INF`（物方无穷远）是**合法写法**，正则只匹配数值记录，不会误伤。

## 影响面

- **`p2_pair_census` 的表头不动**：74 usable / 49 trials 不变 —— 这 8 颗本来就过不了
  产品参数闸。变的是**两闸 seed 池**（192 → 187），这正是
  `upstream-supply-funnel-2026-08-02.md` 第七节说的「放开 seed 池的前置条件」。
- **修不掉坏族**：剔掉这 8 颗后 DATA-10b 中位只从 134.71 µm 降到 82.63 µm、达标仍 0/23。
  SUNNY/KANTATSU 那一档 ~90 µm 是**另一个未定位的病灶**。

## 诚实边界

- **「源表那一格印的就是 `1E+18`」是推断，不是实证**：这 3 件专利的源 HTML 没留档
  （`data/patent-lake` 里找不到 11719917 / 12032139 / 12366724）。
  旁证是 `US-10514523-B2` 的 request 里 38 行 `"radius_mm":1e+18` —— 本库源表确实这么印。
  另：1616 份 `request.json` 里 `thickness_mm ≥ 1e12` 是 **0 行**，
  说明这 8 颗**不是**经本地 replay 那条路转的，它们的请求载荷没留档。
- **本 PR 既不修数据、也不修根因**，只加围堵闸。真修法（标签消费两个 token）另开一铲，
  且必须先解决与 `Aperture plane` 的歧义。
- **本 PR 不修数据**。把这 8 颗的末面 `DISZ` 改成 `0` 再重跑
  trace audit / 重生成 `index.json` 的像高，是**下一铲**——那条路要连带重建 snapshot、
  重生成 golden，并且它们末面的 `DIAM/MEMA`（2.10–3.66）是在被污染的模型上算的，必须重算而非保留。
- 全部为静态分析 + 单元测试，**未跑 CODE V**。
